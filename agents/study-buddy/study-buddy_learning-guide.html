§1 · Use case

What this agent is for

Study Buddy quizzes you on a topic and remembers what you struggled with last time. You name a topic — say, python lists — and it asks you five to eight short questions, one at a time. After every answer it makes a quiet judgment about how confident you sounded on that subtopic and writes a one-line note to a small file on disk. The next time you study the same topic, it opens by drilling whatever was weakest in that file.

The first run will feel like a normal quiz. The second run on the same topic — even with no code changes — will give you a different lesson, because the agent has read its own notes from last time. That's the whole point.

§3 · The agentic core

What makes this an "agent"

Three traits separate a real agent from a clever script. Study Buddy demonstrates all three.

Goal-directedness — it knows when it's done

At the end of every question, the agent asks itself: are we done? That check is a real function in the code that returns yes or no. "Done" means: the model has decided enough has been covered, OR you typed stop, OR the safety cap of eight questions has fired. Whichever comes first wins. The agent never just rambles forever; it has an opinion about completion and it checks that opinion every step.

Autonomy — the model picks the questions, not your code

Your Python doesn't have a hardcoded list like questions = ["What's indexing?", "What's a slice?", …]. Instead, the model is told "here's the topic, here's what was weak last time, ask the user something useful" — and the model picks what to ask, how to phrase it, and what subtopic to drill. Two runs on the same topic produce different questions because the model owns those choices in the moment.

Observe → reason → act, with memory at two layers

This is where Study Buddy really earns the word "agent." After every answer you give, the model assesses it, updates its picture of where you stand, and uses that to choose the next question. That's the within-session loop — and crucially, the model itself remembers what it just asked you (this is new in Cycle 2; the Cycle 1 agent literally couldn't). On top of that, the agent writes confidence notes to a small file on disk after every question, so when you come back tomorrow, it picks up where you actually were. That's the across-session loop.

Both loops are running. Both feed each other. Both are what makes this agent feel aware in a way a quiz script can't.

§5 · Reading the code (a tiny Python primer)

You do not need to write Python to read this agent. You need to recognize five constructs. That's it.

  • def name(args): … — a named recipe. Read the name; the body is the steps.
  • while CONDITION: … — keep doing the indented block until the condition turns false.
  • if … : … else: … — a branch. Take the first block if the test is true, otherwise the second.
  • print("…") — show this text in the terminal. Every emoji-labeled line you'll see during the run is one of these.
  • async and await — black-box for now. Read await something() as "wait here until something() comes back." It's how Python politely lets the LLM take a few seconds to respond without freezing.

Recommended reading order:

  1. Top of main.py — module docstring + constants. Skim the comments labelled PURPOSE; you'll know what each block is for without reading the implementation.
  2. Jump to session_complete(). This is the goal predicate; 7 lines.
  3. Read read_weak_spots() and update_weak_spots(). These touch the across-session memory file.
  4. Read agent_loop() top-to-bottom. This is the main story. Find the async with ClaudeSDKClient(…) as client: line — everything inside that block is one continuous conversation with the model.
  5. Finish with print_summary(). Pure formatting; no logic.

§7 · Watch for these moments

Things worth noticing during the run

The headline moment

The agent remembers what it just asked you — and the second question takes the first one into account. In the previous cycle's agent, every call to the model started fresh; this time, every question after the first is being asked by a model that already knows what came before.

You'll see this in [SESSION MEMORY] lines that grow — "1 turn, 2 turns, 3 turns" — and in the prompts your code sends, which get shorter, not longer, after turn 1. That's the new capability landing.

Two-layer memory in action

Watch for two distinct labels: 💾 [SESSION MEMORY] is the conversation memory living inside the LLM client (gone the moment the run ends), and 📀 [APP MEMORY] is the notes file on disk (survives forever). They do different jobs.

Run it twice

After your first run finishes, run it again on the same topic. Notice the difference. The first turn's prompt now includes "indexing: 0.4 confidence last time" — and the model opens by drilling indexing. No code changed; the agent's behavior did. That's the punchline of this cycle.

The log accumulates

study-buddy_run_output.log is appended every run, never overwritten. By cycle's end you'll have multiple runs side-by-side in one file — useful for the post-run reflection and (in later cycles) for cross-run comparison.

§8 · Gotchas

Watch out for these

  1. First-run empty ledger. If you run on a topic that's never been studied, the agent's "notes from last time" are an empty list. The agent handles this gracefully — it just opens broadly. Don't be alarmed if your first run feels less personalized than the second.
  2. Model wraps JSON in markdown fences. Sometimes the model gets chatty and writes ```json …``` around its structured response. The parser strips fences and extracts the JSON object. If parsing fails entirely, the agent falls back to a safe default rather than crashing.
  3. You hit Enter without typing. An empty answer is treated as low-confidence (the model sees "user gave no answer" and updates the ledger accordingly). The run continues.
  4. The plan can change mid-run. After a surprising answer, the model may abandon the path it was on and switch to a different subtopic — you'll see a 📝 [PLAN REVISED] line. That's not a bug; that's the autonomy trait firing.
  5. Disk write failure. If weak_spots.json can't be written (rare — permissions or disk full), the agent surfaces a ⚠ [ERROR: STRUCTURAL → log] line and continues with the session. The ledger won't update, but the run still completes.

§9 · Control plane

Who's making the decisions

Every interesting choice in Study Buddy is made by one of three deciders. Knowing which is which is the lay version of the question "is this really an agent?"

DecisionWho owns itWhy
Which topic gets studied this runYou (or a constant in code, for the demo)Topic comes from the user; agent doesn't pick what to teach you
Which subtopic to drill firstThe modelIt reads the ledger and decides where the weakness is
How to phrase each questionThe modelSame intent, different wording every run
How confident your answer wasThe modelIt assigns a 0-to-1 score based on your wording
Whether to ask another question or stopThe model — until the cap firesThe cap is your code's last word; before that, the model gets to call it done
When to give up entirelyYou (by typing stop) or the capThe agent never overrides a user-stop

If you replaced the model with a fixed question list and removed the confidence scoring, you'd have a quiz program — not an agent. The agency lives in the rows where the model owns the decision.

§10 · SDK glossary

For readers who want the technical vocabulary:

  • ClaudeSDKClient — the SDK class that holds a persistent conversation. Opened as async with ClaudeSDKClient(options) as client:; closed automatically when the block exits.
  • await client.query(prompt) — sends a new turn into the open conversation.
  • async for msg in client.receive_response(): — pulls messages from the model until a ResultMessage arrives (which marks the end of that turn's response).
  • session_id — a string captured from ResultMessage. With the right rung (6+) you can pass this back to a future query() call to resume the same conversation across separate runs. This agent captures and prints it but does not actively resume.
  • ClaudeAgentOptions — config bag for the client: system prompt, model id, max-turns per call, permission mode, child env.
  • MessageLens — local helper that renders one auditable line per SDK message so the conversation is watchable in the terminal.
  • Rung 3 — the SDK ladder rung introduced by this agent: multi-turn ClaudeSDKClient + session_id capture/resume.

§11 · Self-check

A few self-check questions

Three quick questions. Click Reveal for each after you've picked an answer.

1. Why does this agent's second run on the same topic give a different lesson than its first run?
The agent read its own notes file from the first run. The other two answers are wrong: the model isn't random (it's deterministic enough), and the LLM doesn't change between runs. What changes is the across-session memory layer — weak_spots.json — which the agent reads at the start of every run and folds into the first prompt.
2. Which of these would stop being true if you replaced ClaudeSDKClient with the older query() from Cycle 1?
Each new question would be asked by a model that doesn't remember the previous one. You'd have to re-tell the model everything that happened in prior turns by re-stuffing it into every prompt. The agent could still ask questions and still save notes — those don't depend on the new SDK feature. The model's own memory across turns is what would vanish.
3. If the agent runs all eight questions without the model declaring done, what happens?
The agent stops cleanly at the safety cap; ledger entries written so far are saved. This is the principled-stop trait. The agent has three exit paths — the model says done, you type stop, or the cap fires — and any of the three terminates the loop safely. Partial progress is not lost.
