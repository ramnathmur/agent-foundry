§4 — Two new gotchas: both found on real SDK runs

GOTCHA[query-is-async-generator] — Run 4

await query(prompt=...) raises TypeError: object async_generator can't be used in 'await' expression.

The real claude-agent-sdk query() is an async generator — it uses yield internally to stream SDK message objects. Python's await keyword works on coroutines (regular async def that return a value), not on generators. Awaiting a generator raises TypeError immediately.

Why the smoke tests passed. The smoke test mocks were regular async def functions that returned a SimpleNamespace. Those are coroutines. So await mock_query(...) worked fine, and the mismatch was invisible until the real SDK was called.

What the error looked like in the log:

━━━ [← SDK] 0.0s · ERROR: object async_generator can't be used in 'await' expression

Every sub-agent hit this error, fell into the except block, and returned quality=0.30. G3 fired, follow-ups were dispatched, they all errored too, cap hit at 6/6.

The repair

Replace every await query(prompt=...) with an async for loop that collects the final message:

# Before (broken with real SDK):
result = await query(prompt=...)

# After (works with both real SDK and mock):
result = None
async for msg in query(prompt=...):
    result = msg
if result is None:
    raise RuntimeError("query() yielded no messages")

In main.py this is wrapped in a helper called _run_query(prompt) so the change is in one place, not four. The smoke test mocks were also updated: they now yield instead of return, matching the real SDK's async-generator shape.

# smoke_test.py — mock now matches real SDK shape:
async def mock_query(prompt: str = "", **kwargs):
    yield _make_result(_weather_response(0.9))

After the repair: smoke tests 10/10 green. The real run is now ready.

GOTCHA[result-message-empty-text] — Run 5

ResultMessage.text is empty in the real SDK even on a successful query() call. The actual response text lives in ResultMessage.result (a plain string), not .text.

Why mocks hide it. Smoke test mocks use SimpleNamespace(text=json_string) — they set .text directly. So every mock call works, and the mismatch is invisible until the first real SDK run. Symptom: quality=0.45 across all sections (the parse-fallback value, not the 0.30 error-handler value — meaning the model did respond, but the response text was an empty string).

How the cause was found. A debug print was added to _run_query() that listed all non-callable attributes of each yielded message. The output showed:

┆ [DEBUG MSG] type=ResultMessage attrs=['api_error_status', 'deferred_tool_use', 'duration_api_ms', 'duration_ms', 'errors', 'is_error', 'model_usage', 'num_turns', 'permission_denials', 'result', 'session_id', 'stop_reason', ...]

.result is in the list; .text is not. That was the answer.

The repair (result-message-empty-text)

In _run_query(), check getattr(msg, 'result', None) first when scanning each yielded message, before checking .text or content blocks:

# Check order inside _run_query()'s async-for loop:
candidate = getattr(msg, "result", None)   # 1 — ResultMessage.result (real SDK)
if isinstance(candidate, str) and candidate:
    last_text = candidate
candidate = getattr(msg, "text", None)    # 2 — .text (mocks + some SDK versions)
if isinstance(candidate, str) and candidate:
    last_text = candidate
for block in (getattr(msg, "content", None) or []):  # 3 — AssistantMessage content blocks
    ...

After this fix: Run 6 reached synthesis, model picked calendar as lead, full briefing produced. GOAL MET.

Why the run log also shows three GOAL MET runs before the error run

The smoke tests call asyncio.run(main.main()) directly. The tee_to_log() context manager inside main() appends to the run log on every call — including calls from tests. So all three smoke-test scenarios (happy-path, follow-up, cap-exit) wrote their output to the log, then your real run appended a fourth entry.

This is expected behavior. It also means the log is useful for Part 2 analysis even before a real SDK run completes.

§7 — What heterogeneous sub-agents taught that research-lead could not

Lesson research-lead (homogeneous) morning-intel (heterogeneous)
Follow-up target Any researcher could retry Only NewsScanner can cover a news gap — you cannot send WeatherAnalyst instead
Why isolation matters Sub-agents share a template — isolation is structural but identical Each specialist has a different system prompt, different mock data, different return keys — isolation is functionally meaningful
G2 placement Pre-dispatch: model picks which research angles to pursue Post-collection: model reads three finished sections and picks which leads — the sections shape the decision
Context window born/discarded 5 windows, all reading the same kind of source 3 windows, each reading a completely different domain — weather API, news feed, calendar

The most important consequence of heterogeneous sub-agents: the main agent cannot substitute one for another. In research-lead, if one researcher failed, you could re-dispatch any researcher. In morning-intel, a failed WeatherAnalyst gap can only be filled by another WeatherAnalyst dispatch — the code has to know which specialist type failed and target that specific type. That is what follow_up_history[section_type] tracks.

§8 — Three things to carry forward to Cycle 8

1 · Smoke tests only catch what the mock can simulate

Both gotchas this cycle were invisible to smoke tests. The mocks set .text directly and were regular coroutines — neither the async-generator shape nor the ResultMessage.result attribute was tested. Real SDK runs are the only way to catch SDK interface mismatches. The rule: after any smoke test pass, do a real SDK run before claiming the agent works. And when a real run surfaces a new attribute name, add a debug dir() print before reaching for assumptions — it takes one run and names the fix exactly.

2 · G2 can fire at different moments — both are valid

research-lead: G2 fires before dispatch (model picks which angles to research). morning-intel: G2 fires after collection (model picks which section leads). Neither is more correct. What makes it G2 is that the code offers options and the model chooses — not that the choice happens at a particular step in the loop.

3 · The error handler is part of the agent's architecture

When query() errored, the agent did not crash. It caught the exception, created a low-confidence report (quality=0.30), and continued. G3 then fired because the quality was below threshold. G4 capped the run after 6 dispatches. The agent behaved correctly under error conditions because the error case was designed as a first-class path, not bolted on after the fact.
