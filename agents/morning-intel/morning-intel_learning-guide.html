Section 1

What this agent is for

Morning Intel assembles your morning briefing by sending three independent specialists to work simultaneously — one fetches weather conditions, one scans the news, one reads your calendar — and then combines their reports into a single prioritized brief.

The key word is independent. Each specialist works in complete isolation. The weather specialist has no idea what the news specialist found. The calendar specialist has never seen a weather report. They are hired for one job each, they do it, and they hand in a report. Then Morning Intel reads all three and decides which piece of information is most important for your day.

This is the same underlying pattern as the previous cycle's research agent — but with a twist that matters: in that agent, all the sub-agents had the same job. Here, each specialist has a completely different expertise, and when one fails, you can't ask another to cover for it. The weather specialist cannot fetch news headlines. The architecture forces the agent to care specifically about which specialist is struggling and what different approach to give them.

🌤

WeatherAnalyst

Fetches conditions, forecast, and commute advisory for your location.

📰

NewsScanner

Pulls top headlines filtered by category. Returns the three most relevant stories.

📅

CalendarPrep

Reads today's events and tasks. Highlights high-priority items to keep front-of-mind.

Section 2

How this agent thinks

Morning Intel moves through six stages, in this order:

The three middle boxes — Weather, News, Calendar — run simultaneously and in complete isolation. None of them can see what the others are doing. After all three finish, the agent collects their reports, checks that each one is good enough, then makes a decision about which piece of information matters most today, and writes the final brief.

If a section comes back degraded — say the news scanner returned something thin because the category was too narrow — the agent tries again with different instructions for that specific specialist. It cannot ask a different specialist to cover. It has to give the original specialist a better brief.

Section 3

What makes this an "agent" (in plain English)

Core

It knows what "done" means

Before running a single line of real work, the agent establishes a five-part definition of success. All three sections must arrive. All three must meet a quality bar. A final brief must exist. The agent checks this definition after every action — it doesn't stop because the model says it's done.

Core

It makes its own choices

When all three sections are ready, the agent reads them and decides which one should lead the brief. Stormy weather? Weather section leads. Packed calendar? Calendar section leads. This choice belongs to the model — it is not hard-coded.

Core

It changes based on what it finds

If the news section comes back with a quality score below the threshold, the agent does not simply retry. It changes what it asks for — a different news category, a broader search scope. The next action depends on what the previous one returned.

Deeper dive (skip if not curious): Reading the code

Python Reading Primer — five things to recognize (not write)

  • def — declares a named function: a block of code you can call by name.
  • async def / await — marks code that can pause while waiting for a response. Think of await query() as "wait here until the AI replies." The rest of the program keeps running during the wait.
  • while / for — loops: repeat a block of code a fixed number of times (for) or until a condition changes (while).
  • if / else — branching: "if this is true, do A; otherwise, do B."
  • print() — displays a line in the terminal. Every labeled line you see when you run main.py comes from a print() call.

Guided reading order:

  1. Module docstring (top of file) — AGENTIC TRAITS table gives the full map before you read a line of code.
  2. briefing_complete() — read this first. It tells you exactly what "done" means. Everything else in the file is in service of making this return True.
  3. run_weather_analyst() — the simplest sub-agent. One independent context window, one data fetch, one structured return.
  4. main() — the main loop. Find the for loop, then read the O-R-A block inside it.
  5. The synthesis query() call — find the line labeled [MODEL DECISION]. This is where the model makes the only real choice it owns.

Section 7

Things worth noticing during the run

Sub-agent context windows are born and discarded

Each time you see 📤 [DISPATCHING], a brand-new independent context window starts. The WeatherAnalyst has never seen the NewsScanner's work. By the time 📬 [REPORT RECEIVED] prints, that context window is gone — discarded after handing back its report. What stays is only the structured report itself, which the main agent keeps in its session memory.

The main agent does not remember what the sub-agents reasoned

This agent does not remember what each specialist thought about while working — only what they returned. The weather specialist may have considered three different ways to phrase the commute advisory, but by the time the report arrives, that reasoning is gone. This is the same principle as session notes versus a shared database: useful during the engagement, gone when the consultant leaves.

This also means that on the next run, the specialist starts completely fresh with no memory of yesterday's brief. The only cross-run memory lives in morning-intel_briefing_log.json, which the main agent writes on a successful exit.

The follow-up path is the teachable moment

If you see 🔄 [LOOP FEEDBACK] followed by a second 📤 [DISPATCHING] for the same specialist, that is the agent doing something different rather than just trying again. Watch what parameter changed in the second dispatch call — that is the act-strategy adaptation.

Run log accumulates across every run

morning-intel_run_output.log grows with every run you do. After a few runs you can open it and compare: did the model choose the same lead section both times? Was the quality score different? The log is the raw material for Part 2 of this guide, which you will read after running the agent.

Section 8

Watch out for these

These are the known traps that show up in code like this. Morning Intel is written to avoid them — but knowing they exist will help you read the code and understand why certain lines are there.

  • Sub-agents cannot cover for each other. If the news specialist returns low quality, you cannot send the calendar specialist to check the news. The follow-up logic has to know which specialist type to reissue to. This is the defining constraint of heterogeneous sub-agent architectures.
  • The model's summary is not the goal check. The model might say "I have everything I need for a great briefing" — and the goal predicate might still return False, because the quality score for one section is 0.55. Text statements from the model are not evidence. The predicate decides.
  • Silence between ALLOW and execution is a clue. If you have used permission controls in prior agents and carried that pattern here, remember: a missing [REPORT RECEIVED] after a [DISPATCHING] line is diagnostic — something silently failed between dispatch and return. Look for what print statement is absent, not what error message appeared.
  • The sub-agent context is isolated on purpose. If you see a sub-agent return a report that looks uninformed — it didn't know about the other sections, because it was not supposed to. Shared context between sub-agents would compromise the independence of their outputs. The isolation is a feature, not a bug.
  • Note: the "plan revised" banner does not fire in this agent. Morning Intel's plan is structurally fixed — dispatch three specialists, collect, synthesize. The plan-revised moment fires when the model encounters an unexpected tool result and restructures mid-task. That behaviour first appeared in a later cycle.
Section 9

Who's making the decisions

The code owns

Whether all three sections have been received. Whether each section met the quality threshold (0.6). Whether the hard caps have been reached. The decision to dispatch a follow-up. The decision to stop.

The model owns

Which section leads the morning brief (weather urgency, calendar priority, or news significance). The actual text of the final briefing. The phrasing and emphasis within each synthesized section.

The specialists own

How to format and phrase their section given the raw data. Whether the data they found is complete enough (reflected in the quality_score they return).

If Morning Intel were a plain script (not an agent), the lead section would be hardcoded — weather always leads, or calendar always leads. You would lose the model's judgment about what actually matters today. The 🎲 [MODEL DECISION] line in the output marks the exact moment that judgment happens.

Section 11

A few self-check questions

1. The NewsScanner returns a section with quality_score = 0.55. What does Morning Intel do?
  • Discards the news section and writes the brief without it.
  • Dispatches the NewsScanner again with different parameters.
  • Asks the CalendarPrep specialist to cover the news gap.
  • Accepts the section — 0.55 is close enough to the threshold.
Correct. The main agent identifies that news quality is below the 0.6 minimum, then reissues a brief to the NewsScanner specifically — with a different category or broader framing. It cannot substitute another specialist type. Wrong answers: discarding a section makes the goal predicate permanently unsatisfiable; substitution is the key mistake this architecture is designed to prevent; 0.55 is below threshold and the predicate enforces the check.
2. Which line in the terminal output proves this is an agent (not just a script that calls three functions)?
  • 📤 [DISPATCHING: weather-analyst] — the agent sent a specialist.
  • 🎲 [MODEL DECISION] lead=calendar — the model made a choice the code didn't hard-pick.
  • 📋 [PLAN GENERATED] — the agent made a plan.
  • 🏁 [GOAL MET] — the agent finished successfully.
Correct. The [MODEL DECISION] line is the evidence that a real branching choice was made by the model at runtime, not pre-determined by the code. A plain script would always lead with the same section. Wrong answers: dispatching specialists is mechanical (the code decides to dispatch, not the model); a plan is still code-driven; GOAL MET just confirms the predicate passed.
3. WeatherAnalyst finishes before NewsScanner returns. Can WeatherAnalyst's context window see the news data that arrives later?
  • Yes — the main agent shares all incoming reports with all active specialists.
  • No — WeatherAnalyst's context window closes when it returns its report. It no longer exists by the time the news data arrives.
  • Only if the main agent explicitly forwards the news data to WeatherAnalyst.
Correct. Each sub-agent's context window is created, used, and discarded when the sub-agent returns its report. There is no shared memory between sub-agents. This is the key isolation property that makes independent sub-agents useful — if they shared context, their outputs couldn't be independently combined. Wrong answer (forwarding): even if you tried, there's no mechanism to send data to a context window that has already closed.
4. The agent hits MAX_SUBAGENTS = 6 without briefing_complete() returning True. What does this mean?
  • The agent is broken — a working agent always reaches its goal.
  • The agent stopped correctly — reaching the cap with the goal unmet is a principled stop, not a failure.
  • The agent will loop indefinitely until the goal is met.
Correct. A principled stop via hard cap is a governance exit, not a broken agent. The exit line says [EXIT: sub-agent cap] — the agent explains why it stopped. The goal was not met, but the agent behaved correctly by enforcing its own limit. Wrong answer (broken): an agent without a cap that loops forever is the broken one. Wrong answer (infinite loop): hard caps are code-enforced, not optional.
Section 12

Before you hit Run

Five things to confirm before you open PyCharm:

  • You can say in one sentence what the goal predicate checks — it has five conditions, not one.
  • You know which output line marks the model's only real decision (the lead section choice).
  • You understand why the NewsScanner can't be replaced by the CalendarPrep if it fails — and what the agent does instead.
  • You know where the sub-agent context windows are created, and when they disappear.
  • You have claude auth status passing and claude-agent-sdk installed (see README.md for the one-line install).
