🔬 Research Project Lead

Learning Guide (Part 1) — Read this before you run the agent

1 What this agent is for

You give this agent a research question. It breaks the question into angles — say, the technical side, the user-experience side, and the contrarian "what could go wrong" side — and sends a specialist researcher to investigate each one independently. When the specialists report back, the agent reads their findings, checks for gaps, and writes a single briefing that pulls everything together.

The big idea: This is a project lead that delegates, not a researcher that does everything alone. The specialists work independently and don't see each other's notes. The lead only sees their final reports — never their internal thinking. That boundary is the teaching point of this agent.

2 How this agent thinks

This agent runs a two-level loop. The top level is the project lead. The bottom level is each specialist researcher. Here's the lifecycle:

Notice the dashed boxes in the middle row — each specialist runs in its own isolated space. The project lead at the top can't peek inside those boxes; it can only read the report that comes out at the bottom.

The dashed loop-back arrow on the right is the learning moment: if the project lead reads a report and finds a gap ("this angle missed something important"), it sends another specialist to investigate — but only up to a hard limit of 5 total specialists.

3 What makes this an "agent" (in plain English)

Three things separate this from a script that just runs a sequence of steps:

🎯
It knows what "done" means
After every major action, the agent runs a checklist: did all specialists report back? Is there a synthesis? Is the confidence high enough? If any answer is no, it's not done — regardless of how many steps it's taken.
🎲
It makes its own choices
The code offers six research angles, but the agent picks which three to five to actually investigate. A different run on a different question might pick completely different angles. The code doesn't prescribe the sequence.
🔄
It learns from what it sees
After reading the specialists' reports, the agent checks each one for gaps and weak confidence. If something is missing, it dispatches a follow-up. Its next action depends on what came back — not on a pre-set plan.
🔬
It delegates to independent workers
Each specialist researcher works in its own separate space — it can't see the project lead's strategy or the other specialists' findings. The project lead only receives the final report. This is the new concept in this agent.
Section 4 — Deeper dive (skip if not curious): Where each trait lives in the code

Goal-directedness — main.py defines is_goal_met(state) which checks three conditions: all dispatched sub-researchers have returned, a synthesis exists, and confidence meets the 0.7 threshold. Called after every major action.

Autonomy (model's own choice) — When the main agent receives the research question, the model decides which angles from the six-option palette to investigate. The code registers all six as options but never prescribes which ones to pick.

Observe-reason-act — In main.py, after collect_reports() returns, the agent inspects each report's gap_flagged and confidence fields. If gaps exist or confidence is below 0.6, it calls spawn_researcher() again with the specific gap as the question. This is a closed loop.

Independent context (rung 8) — Each sub-researcher creates its own ClaudeSDKClient instance in run_sub_researcher(). The main agent's context window never contains the sub-researcher's messages — only the structured report it returns.

Section 5 — Deeper dive (skip if not curious): Reading the code

Python Reading Primer (5 things to recognise)

You don't need to write Python — just recognise these five patterns when you see them:

  1. def function_name(...): — defines a reusable block of instructions. Think of it as naming a procedure.
  2. while condition: / for item in list: — repeats the indented block. The agent loop is a while.
  3. if / else: — a branching decision. "If this is true, do A; otherwise do B."
  4. print(...) — writes text to your terminal. Every labeled output line you'll see comes from a print().
  5. async / await — think of await as "wait here until the AI responds." It's a black box; you don't need to understand the mechanism.

Guided reading order

  1. Start at the bottom: if __name__ == "__main__": — the entry point. This calls preflight() then main().
  2. Read main(): The main agent loop. Find the while — that's the heartbeat.
  3. Find is_goal_met(): The did-it-finish check. Three conditions, all must be true.
  4. Find run_sub_researcher(): This is where a new, independent context window is created. Notice it creates its own client — separate from the main agent's.
  5. Skim the tools: spawn_researcher, collect_reports, synthesize_briefing — three tools the main agent can call. Then lookup_source, extract_finding, summarize_findings — three tools each sub-researcher can call.

7 Things worth noticing during the run

🧩 The specialists can't see each other

Each box-drawn specialist section in the terminal runs in complete isolation. The technical researcher doesn't know the user researcher exists. They can't coordinate, share notes, or copy each other's work. The project lead is the only one who sees the full picture — and even then, it only sees the summary reports, not the internal reasoning.

🔄 The follow-up loop is where learning happens

If the project lead reads a report and finds a gap, it doesn't just note it and move on — it sends another specialist. Watch for the [LOOP FEEDBACK] line that says something like "1 report has gap_flagged=True → dispatching follow-up." That's the agent adapting to what it found.

💾 Each specialist starts fresh

The specialists don't remember anything from the main agent's conversation. Each one starts fresh with only its assigned angle and question. In a future agent, you'll see how to give specialists access to prior context — but here, isolation is the teaching point.

📝 The run log accumulates

Every run appends to research-lead_run_output.log in the agent folder. This log is the raw material for the post-run learning file. In later cycles, you'll be able to compare runs side by side.

8 Watch out for these

⚠️
The specialists work with a mock database, not the real internet. Everything they "find" comes from a pre-loaded set of research entries. This means the agent's findings are scripted — but the agent's behaviour (which angles to pick, whether to follow up) is real. Focus on the behaviour, not the content.
⚠️
A cap exit is not a failure. If the agent hits its limit of 5 specialists without finishing, that's the safety cap doing its job. The agent will label its exit clearly — "EXIT: subagent cap" — so you know it stopped on purpose. The execution succeeded; the goal didn't.
⚠️
The model might pick different angles each time. Since the model decides which angles to investigate, running the same question twice might produce different dispatches. That's not a bug — it's the autonomy trait in action.
⚠️
Sub-researcher context is invisible to the main agent. If you're reading the code and wonder why the main agent doesn't seem to know something a sub-researcher found — that's the context boundary. The main agent only knows what's in the sub-researcher's final report.

9 Who's making the decisions

This agent has three decision-makers — more than any agent you've seen so far:

Decision Who makes it
Which angles to investigate The main agent's model — picks from 6 options
How to search and extract findings Each sub-researcher's model — works independently
Whether to dispatch a follow-up The main agent's model, guided by gap/confidence thresholds
Whether the goal is met The code — a computable checklist, not the model's opinion
When to stop on safety cap The code — hard limits on total specialists and synthesis attempts
If this were a workflow instead of an agent: a workflow would hard-code "always investigate technical, market, and user" — every run would pick the same angles. An agent reads the question and decides which angles actually matter for this question. That's the difference.
Section 10 — Deeper dive (skip if not curious): SDK glossary

ClaudeSDKClient — The connection between your Python code and the AI model. Each client maintains its own conversation history. This agent creates multiple clients: one for the project lead, one for each sub-researcher. That's what makes them independent — they literally have separate conversations with the model.

@tool — A way to register a Python function so the AI model can call it. The model sees the tool's name and description, then decides when to use it. Six tools are registered in this agent (three for the main agent, three for sub-researchers).

query() — Sends a single message to the model and gets a response. Used here for sub-researcher turns (each sub-researcher makes a small number of focused calls).

Subagent — A second agent spawned by the first, with its own context window. The parent agent (project lead) doesn't see the subagent's internal messages. This is rung 8 of the SDK ladder — the most advanced concept introduced so far.

Context compaction — When a sub-researcher finishes, its entire reasoning chain (all the messages back and forth) is compressed into a single structured report. The main agent works with the compact report, not the raw conversation. This is how real multi-agent systems manage their context budget.

11 A few self-check questions

1. Why does each specialist researcher run in its own separate space?
  • a) To make the code simpler
  • b) Because the AI can only handle one conversation at a time
  • c) So that each researcher works independently without being influenced by the others' findings
  • d) To save on cost
Correct: (c). The isolation is deliberate — it models real research teams where specialists work independently to avoid groupthink. The project lead is the only one who sees the full picture. Cost savings are a side effect, not the reason.
2. The agent hit its safety cap of 5 specialists without producing a synthesis. Is this a broken agent or a working one?
  • a) Broken — it should always produce a synthesis
  • b) Working — the cap is a governance mechanism; the agent correctly stopped and labelled why
  • c) Broken — the cap should be higher
Correct: (b). A cap exit is a principled stop, not a failure. The agent labelled its exit reason ("EXIT: subagent cap") so you know exactly why it stopped. The execution was successful — the goal just wasn't reached within the budget. Same pattern you saw in earlier agents.
3. What's the difference between this agent and a script that always researches "technical, market, and user"?
  • a) This agent reads the question and picks whichever angles fit best — the choice could change every run
  • b) There's no real difference — the code still limits it to six options
  • c) The script would be faster
Correct: (a). The agent's model decides which angles to investigate based on the question. A question about privacy law might get "regulatory" and "contrarian" where a question about learning methods might get "user" and "historical." The code offers options; the model makes the choice. That's the autonomy trait.
4. When the project lead reads a report with a gap, what does it do?
  • a) Ignores the gap and moves on to synthesis
  • b) Asks the same specialist to try again
  • c) Dispatches a new specialist to investigate the specific gap
  • d) Stops and reports the gap to the user
Correct: (c). This is the observe-reason-act loop: the agent observes the gap in the report, reasons that it needs more information, and acts by spawning a follow-up specialist targeted at that specific gap. The specialist is new (it has its own fresh context), not the original one retrying.
5. Can the project lead see the specialist's internal thinking?
  • a) Yes — the lead has access to everything
  • b) No — the lead only sees the specialist's final report, not its internal reasoning
  • c) Yes, but only after the specialist finishes
Correct: (b). This is the core rung-8 concept — context isolation. The specialist's entire conversation with the model happens in a separate space. The lead receives a structured report (the "compacted" version). This is how real multi-agent systems work: you delegate, you get results, but you don't micromanage the internal process.

12 Before you hit Run

Takeaway: This is the first agent that delegates to other agents. Everything you've built before — goals, choices, loops, caps — is here, but now there's a second level: independent workers with their own context windows. The boundary between what the lead knows and what the specialists know is the new concept to watch.
  • You know what the agent's "done" checklist looks like — three conditions, all required (section 3)
  • You understand that the specialists work in isolation — they can't see each other or the lead's strategy (section 2)
  • You can spot the model's own choice in the output — the angle selection (section 6)
  • You know that a cap exit is a working safety mechanism, not a bug (section 8)
  • You recognise the loop-back moment — when the lead reads a gap and dispatches a follow-up (sections 2 and 7)
