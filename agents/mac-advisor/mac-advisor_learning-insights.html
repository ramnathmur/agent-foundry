Agent Foundry · Cycle 4 · Part 2 (post-run)

Mac Advisor — what just happened

An agent that ran exactly as designed — and taught us something we didn't know to look for.

1About this run

The setup — what this agent was trying to do

The agent's role
A research assistant whose job is to recommend the best MacBook Pro M4 variant for a software developer who also does AI work, buying in India.
The specific question this run answered
Of the M4 Base, M4 Pro, and M4 Max, which is the right fit — and what does it cost?
What counts as "done"
Two checks must both pass: research is complete across four areas (specs, pricing, thermal performance, comparisons), AND the agent has produced a recommendation it's at least 80% confident in.
The safety limit (and who set it)
We set it — a maximum of 8 research turns and 3 synthesis turns. The agent did not choose this. It's a guardrail we put around it so it can't run forever.
The tools the agent had
Five — look up specs, check current price, analyze thermal performance, compare two variants, and produce the final recommendation. Crucially, only four of these were available during research; the fifth (recommendation) was locked until research was complete.
A caveat about the data
The research databases are mocked — realistic but pre-seeded numbers (₹2,49,900 starting price for M4 Pro 24GB, AnandTech thermal data, etc.). The agent's reasoning is real; the world it reasoned about is a controlled simulation.

The headline

This run did not produce a recommendation — and that is not a failure. The agent worked correctly: it gathered evidence, spotted a contradiction, and stopped when it couldn't resolve the contradiction within the safety limit. What it surfaced is a design lesson that's worth more than the recommendation would have been.

2Was this really an agent? Here's the proof

The most important section of this document. Three plain-English questions, each answered with one line the agent actually printed during the run.

Did the agent decide when it was done?

   (specs=3≥2, price=2≥1, thermal=True, resolved=False, compare=True)

Yes. At every turn, the agent ran its own checklist and reported the result. Notice the detail in parentheses — the agent shows which items it has and which it's missing. The flag resolved=False meant "I still have an unresolved contradiction; I'm not done." The agent didn't ask us. It checked itself.

✓ The agent owned the done-decision.

Did the agent choose its own next move?
🎲 [MODEL DECISION] selected 11 tool call(s) from research palette · alternatives: different tool, different params, stop

Yes — and at industrial scale. In turn 1 alone the agent freely selected eleven tool calls across four different tools: look up specs for three variants, check prices for two SKUs, run thermal analysis on two workloads, and run two head-to-head comparisons. The Python code didn't sequence these. The model picked, in real time, which tools to use and in what order.

✓ The agent picked its own playbook.

Did the agent learn from what it saw?
⚠ [CONFLICT DETECTED] thermal data contradiction for m4_pro
  ── O ──  Source 1 (Apple white paper 2025): 'none detected'
  ── O ──  Source 2 (AnandTech independent review 2026-04): '15-20% under sustained AI inference'

Partially — and this is where the run got interesting. The code-side of the agent learned brilliantly: it saw the contradiction between Apple's claim and the independent lab's measurement, named the conflict, and computed exactly what to do about it. But the model-side — the LLM at the heart of the agent — never received that resolution instruction in its next briefing. From that point on, it could see "conflict unresolved" as a flag, but had no idea what action would resolve it.

✓ Partially — and the gap is the most valuable thing this run revealed. See §3.

3Why this goal counted as a real check

There are two ways an agent can decide it's done. One is a wish — "I think I've covered enough." The other is a test it runs on itself — a checklist where every box has to be tickable from the current evidence, or the answer is "not yet."

This agent took the second path. At every turn it computed a boolean — true or false — from its current state. The line you saw in §2:

📐 [GOAL PREDICATE] is_research_complete(state) → False
   (specs=3≥2, price=2≥1, thermal=True, resolved=False, compare=True)

That's the test. Five subconditions, all needing to be true. Four were satisfied. One — the requirement that any spotted contradictions be resolved — wasn't. So the answer was False, and the loop continued. The agent didn't "feel" undone. It was undone by an unambiguous, computable test it could not yet pass.

Here is what's powerful about this: the agent could not lie to itself. In turn 1 it actually said "RESEARCH COMPLETE" in its own text. The checklist disagreed, because resolved was still False. The checklist won. That is what separates an agent that knows what done means from a hopeful loop that stops when the model feels confident.

For a non-coder, the right analogy is a project sign-off form. A PM can feel the project is done — but until every box on the form is ticked, the project is not signed off. The form is the truth. The feeling is just a feeling.

The technical view: the SDK call sequence

The Python loop opened a ClaudeSDKClient in the research phase with allowed_tools = [search_specs, check_price, analyze_thermal, compare_variants] and permission_mode = "dontAsk". Each iteration emitted a [SDK →] marker, awaited the model's reply, parsed the resulting messages for ToolUseBlocks, and emitted a [← SDK] close marker. The "dontAsk" permission mode is what made the synthesize_recommendation block in turn 2 a hard denial rather than a permission prompt.

7Agent Spectrum Placement

Where does Mac Advisor sit on the spectrum from rigid workflow to fully autonomous agent?

Workflow
Simple Agent
Multi-Step Agent
Autonomous Agent

Mac Advisor is a multi-step agent. It has a fixed plan structure (research → synthesis), but within each phase the model has genuine choice about which tools to use, in what order, and how many to call per response. The eleven-tool sequence in turn 1 wasn't scripted — the model improvised it.

If this were a workflow instead, the code would have looked like: specs = search_specs(); price = check_price(); thermal = analyze_thermal(); recommendation = synthesize(). Four lines, fixed order, no choice. The model would never have spotted the thermal conflict on its own, because it would never have decided to call analyze_thermal twice with different workload parameters. That's the difference — and you can point to it on this line:
🎲 [MODEL DECISION] selected 11 tool call(s) from research palette · alternatives: different tool, different params, stop
The phrase "alternatives: different tool, different params, stop" is the proof. The model had options. The model chose. A workflow has no alternatives — it just does the next line.

10What you could build next

An agent that learns from yesterday's runs

Mac Advisor remembers findings between runs, but it remembers everything. A smarter version would write a summary at the end of each run ("M4 Pro is the leading candidate; thermal conflict unresolved") and read only what's relevant the next morning. The technical term is episodic memory.

An agent whose handoffs always work

The big lesson of this run: when the code spots something the model needs to do, the only place that signal counts is the model's next briefing. An agent that systematically writes "clearance register" entries into the model's context — every time, automatically — would not have hit Mac Advisor's wall.

An agent you can audit after the fact

Right now, the only audit trail is what gets printed to the terminal. Imagine being able to inspect every tool call before it ran, attach reasons, block invalid ones, and write the whole story to a machine-readable log. That's the next rung up.

An agent that asks for help

Mac Advisor never escalated to a human when it got stuck. It just kept saying "nothing to do" until the cap fired. An agent with a structured escalation path — "I'm blocked because X; need your input" — would have surfaced the problem in turn 3 instead of turn 8.
