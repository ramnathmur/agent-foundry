1. What this agent is for

Mac Advisor researches the MacBook Pro M4 lineup and recommends the best model for a software developer and AI practitioner working in India. You give it nothing except your workload — it goes off and researches specs, pricing, thermal performance under load, and head-to-head comparisons entirely on its own. When it hits contradicting information from two sources, it detects the conflict and resolves it before drawing any conclusions. When the price of its top pick drops mid-research, it notices and updates its reasoning.

By the end of a run, you have a purchase recommendation — with the evidence trail visible in your terminal the entire time.

2. How this agent thinks

The agent loops through the Research → Look → React cycle until it has covered all four areas (specs, pricing, thermal, comparison). Only then does the menu change and the Synthesise step becomes available. The loop has a safety limit: if research isn't complete within eight turns, the agent stops and reports what it found.

3. What makes this an "agent"

It knows what done means

At every step, the agent runs a check on its own state: "Have I researched specs for at least two variants? Has at least one price been verified? Has any thermal conflict been resolved?" Only when all four research areas pass that check does the agent consider research complete. The check is a yes/no calculation — not a vague sense of readiness.

It owns its own moves

You tell the agent the goal (recommend a MacBook for my workload) and the agent decides which tool to call at each step. Should it check specs first or pricing? Which variant is worth comparing? When it hits a thermal conflict, does it need one more data point or two? Those choices belong to the agent, not your code.

It learns from what it sees

When the first thermal source says "no throttling" and the second says "15–20% throttle," the agent doesn't average them or pick one at random. It flags the contradiction, explains what it saw, and runs a targeted follow-up before continuing. The second thermal call is different from the first precisely because of what the first call returned. That's the observe–reason–act loop made visible.

Deeper dive (skip if not curious): where each trait lives in the code
  • Goal predicate — is_research_complete() + is_recommendation_ready() in main.py, called after every turn
  • Model decision — send_turn() and every [MODEL DECISION] line: the model picks which tool to call from the current phase's allowed palette
  • Observe–reason–act — _mock_state["thermal_conflict_pending"] flagged by _analyze_thermal_impl(); checked and printed in agent_loop() after each turn
  • Rung 5 — build_options(child_env, phase): allowed_tools=RESEARCH_ALLOWED in research phase; allowed_tools=SYNTHESIS_ALLOWED + disallowed_tools=RESEARCH_ALLOWED in synthesis phase
Deeper dive (skip if not curious): reading the code — Python primer

Five things to recognize (you don't need to write them — just read them):

  • def / async def — defines a function. async def means "this function waits for the SDK."
  • while / for — repeats steps. The research loop is a while that keeps going until the predicate returns True.
  • if / else — makes a decision. The phase switch is an if phase == "research": block.
  • print() — writes one line to your terminal. Every labeled line you see in PyCharm is a print().
  • await — "wait here until the SDK responds." Think of it as a pause button that lets other things run while waiting.

Reading order: start with the constants at the top → read is_research_complete() and is_recommendation_ready() → read build_options() (the rung 5 function) → skim agent_loop() top to bottom.

7. Things worth noticing during the run

Each call to the model starts fresh — with one exception

Within each phase, the agent uses a persistent conversation — the model remembers what it asked and what came back across turns in the same phase. But when the phase switches from research to synthesis, a new conversation starts. The model in synthesis only sees what you hand it — the summarised research findings. It can't scroll back through the research turns. A future capability will let you carry full conversation history across phases — that's not this agent.

The thermal conflict is the best moment to watch

When you see ⚠ [CONFLICT DETECTED], notice what happens next. The agent doesn't ignore one source or crash. It explains what it observed, reasons about what the contradiction means, and makes a different tool call than it otherwise would have. That change in behaviour — caused by an observation — is exactly what the observe–reason–act loop looks like in practice.

Your run output will be saved

Every run appends to mac-advisor_run_output.log. This file becomes the evidence base for Part 2 of this learning set (the Insights document), which you'll generate after your first run.

8. Watch out for these

  • env dep preflight failure — if PyCharm can't find claude_agent_sdk, the agent exits immediately with a fix-it message. Check that your virtual environment is activated and pip install -r requirements.txt has been run.
  • no API key needed — if you see an authentication error mentioning ANTHROPIC_API_KEY, do not set it. The agent uses your Claude Max subscription via the CLI. Run claude auth status to verify your login.
  • handler attribute on decorated tools — the @tool decorator wraps each function into an object. If you're writing a test and try to call search_specs_tool({"variant": "m4_pro"}) directly, it will fail. Use search_specs_tool.handler({"variant": "m4_pro"}) instead.
  • two termination paths — the agent can stop for two different reasons: it finished (recommendation ready) or it hit the safety cap. Both are working correctly. A cap exit isn't a failure — it means the agent respected the limit you set.

9. Who's making the decisions

This is the most important section for Cycle 4. The new capability in this agent — rung 5 — is about who controls what the model is allowed to do.

What changed from the last agent

In the previous agent (recipe-companion), all five tools were registered and the model could call any of them at any time. The system prompt said "do these steps in order," and the model mostly followed. But "mostly" is the important word: a system prompt is a request, not a lock. The model could, in principle, call any tool whenever it felt like it.

In mac-advisor, we've changed something structural. Python controls which tools the model is even allowed to call — and that control changes mid-run.

The two menus

🔬 Research Phase

search_specs ✓ allowed
check_price ✓ allowed
analyze_thermal ✓ allowed
compare_variants ✓ allowed
synthesize_recommendation ✗ denied

The model cannot commit to a recommendation yet — the tool doesn't exist from its point of view.

🔮 Synthesis Phase

search_specs ✗ denied
check_price ✗ denied
analyze_thermal ✗ denied
compare_variants ✗ denied
synthesize_recommendation ✓ allowed

The model cannot keep researching indefinitely — the only move available is to produce the recommendation.

Why this matters more than a system prompt

If you only used a system prompt to say "don't call synthesize_recommendation during research," the model would usually comply — but nothing in the code would stop it from slipping. With allowed_tools and permission_mode="dontAsk", the SDK enforces the boundary. If the model attempts to call a denied tool, the call is blocked. The model is not asked nicely — it simply has nothing to call.

This is how production agents enforce workflow ordering without writing brittle if/elif/else control flow in Python. The model owns the decisions within each phase; your code owns the boundary between phases.

The workflow-to-agent distinction for this agent: a workflow would hard-code "first call search_specs, then check_price, then analyze_thermal." This agent lets the model decide the research sequence — it just can't commit to a recommendation until research is done. That's the difference between giving the model a script and giving it a goal with guardrails.
Deeper dive (skip if not curious): the three rung 5 SDK parameters
  • allowed_tools=["mcp__advisor__search_specs", ...] — the list of tools the model is permitted to call. In the research phase, this is the four research tools.
  • disallowed_tools=["mcp__advisor__search_specs", ...] — an explicit block list. In the synthesis phase, both allowed_tools and disallowed_tools are set — belt-and-suspenders.
  • permission_mode="dontAsk" — the rule for anything not in allowed_tools: deny immediately, don't prompt. Compare to "bypassPermissions" from the previous agent, which allowed everything.

All three are set in build_options(child_env, phase) in main.py.

Deeper dive — SDK glossary (section 10)
  • claude-agent-sdk — the Python library that handles communication between your code and the Claude model. Used in every Foundry agent.
  • ClaudeSDKClient — the conversational client. Holds a running conversation (turns) so the model remembers what happened before.
  • @tool / create_sdk_mcp_server — how custom tools are registered. The model can call them natively; Python doesn't dispatch them manually.
  • allowed_tools / disallowed_tools — rung 5. Set in ClaudeAgentOptions; controls which registered tools the model can actually call.
  • permission_mode="dontAsk" — rung 5. Any tool not in allowed_tools is denied without prompting.
  • query() — sends one message to the model and waits for a response (which may include tool calls).

11. A few self-check questions

1. During the research phase, the model tries to call synthesize_recommendation early. What happens?

A) The model gets an error message explaining why it failed.
B) The call is blocked by the SDK — the tool isn't in allowed_tools.
C) The system prompt tells the model to stop, and it does.
Not quite — it's not an error message. The SDK blocks the call at the permission level.
Correct. permission_mode="dontAsk" means the call is denied, not prompted. The model doesn't see the tool at all during the research phase.
This is how a workflow would handle it — using instructions. An agent using rung 5 enforces it structurally, not via text.

2. The agent's goal predicate checks whether the tool-call log shows certain tools were called. Why not just check what the model says it did?

A) The model's words are accurate, but checking tool logs is faster.
B) Language is unreliable as a completion signal — the model can say "done" before all conditions are met.
C) The tool logs are the only place where result data is stored.
Not quite — the problem is reliability, not speed. The model can say "RESEARCH COMPLETE" before all four areas have been covered.
Correct. The predicate trusts the tool-call log because it's deterministic. The model's text is a hint, not a guarantee. Both exist in this agent — but only the predicate controls the loop.
Partially true, but that's not why. The key reason is that language alone can't be trusted as a stopping signal.

3. Is mac-advisor a workflow or a real agent?

A) Workflow — the research steps are predetermined.
B) Agent — the model chooses which research tool to call at each step, and the goal predicate (not a script) controls when phases end.
C) Neither — it's a pipeline.
The research areas are predetermined (specs, price, thermal, compare), but the sequence and which tools to call at each step are the model's choice. That's not a workflow — it's a goal with guardrails.
Correct. The model picks tools, detects conflicts, and decides when enough data has been gathered. The phase gate is code-enforced, but the moves within each phase are model-owned.
A pipeline would run in a fixed order. This agent adapts based on what it observes — the thermal conflict causes a different tool call sequence than a clean run would.
