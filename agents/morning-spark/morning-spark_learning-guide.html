Section 01

What Morning Spark Does

Morning Spark is a morning briefing agent. Every time it runs it does exactly one thing: produce a short morning briefing that tells you the weather, the date, and a top news headline.

To do that it calls five tools in sequence — fetch the weather, fetch today's date, fetch a headline, check that all three sources came back with real content, and then synthesise a briefing from them.

What makes this cycle interesting is not the briefing. It's what happens at the moment each tool is called. Two hooks fire on every tool — one before it runs, one after it returns. Those hooks are the entire point of Cycle 6.

Learning position: FORWARD. Rung 6 (hooks) has not appeared in any prior cycle. Everything you see here is new SDK territory.

A hook is a function you register with the SDK. The SDK calls it automatically at a specific moment in the tool execution path — you don't call it yourself, and you can't accidentally forget to call it. It always fires.

The key idea: hooks let you put code inside the SDK's execution pipeline, not just around it. Everything you've built so far sits outside the pipeline — your loop runs before and after the SDK does its work. Hooks get you in between.

Section 03

The Interception Window

Analogy — the airport security checkpoint

Think of an airport. When a passenger approaches the gate, there are two checkpoints: security (before boarding) and the door scanner (after boarding but before take-off). Security can deny boarding entirely — the passenger never gets on the plane. The door scanner logs who actually got on.

These are two separate moments, with two separate jobs: intercept before, record after.

Why it matters — code can now act at the moment of execution

In every prior cycle, your Python loop could read what the model said it wanted to do (dispatch a tool call) and read what the tool returned — but there was no way to intervene in the middle. The model dispatched, the tool ran, the result came back. That's all you could observe.

With hooks you can stop a tool from running altogether, or capture a structured record the moment after it succeeds. That's a qualitatively different level of control.

In the SDK
# Two hook types, one for each side of the execution window
ClaudeAgentOptions(
    hooks={
        "PreToolUse": [HookMatcher(matcher=None, hooks=[pre_tool_use_guard])],
        "PostToolUse": [HookMatcher(matcher=None, hooks=[post_tool_use_audit])],
    }
)

matcher=None means "match every tool call." Both hooks fire on all five Morning Spark tools.

Open question — before reading further

If you had a function that fires before every tool call, what's the most dangerous thing you could do with it? And what's the most useful?

Section 04

The PreToolUse Guard

Analogy — the loan officer's checklist

A bank loan officer receives an application. Before the application ever reaches underwriting, an intake officer runs a pre-check: is the form complete? Has this application already been submitted today with identical figures? If the answer is yes — same applicant, same amount, same terms — the intake officer returns it immediately. "Already reviewed. You need different terms to proceed." The underwriter never sees the duplicate.

Why it matters — strategy change at the execution boundary

In Cycle 5 (research-lead), follow-up sub-agents dispatched back to the same source with the same search parameters and got the same insufficient result. The loop detected a gap and tried again — but "trying again" with identical parameters is not trying differently.

The PreToolUse hook fixes this structurally: it records every (tool_name, params) pair that has been tried. If the model tries to call fetch_headline with category="technology" a second time, the hook denies it before the tool executes and explains why. The model must choose a different category.

In the SDK
async def pre_tool_use_guard(input_data, tool_use_id, context):
    sig = (input_data.tool_name, json.dumps(input_data.tool_input, sort_keys=True))

    if sig in _hook_state["calls_made"]:
        _hook_state["denied_count"] += 1
        return {
            "hookSpecificOutput": {
                "hookEventName": "PreToolUse",
                "permissionDecision": "deny",
                "permissionDecisionReason": (
                    f"Tool '{input_data.tool_name}' with these parameters has already been "
                    f"called. Try a DIFFERENT category for fetch_headline, or proceed "
                    f"to check_quality if you have weather, date, and a headline."
                ),
            }
        }

    _hook_state["calls_made"].append(sig)
    return {}
Open question

What happens to the model's next turn when a PreToolUse hook returns permissionDecision: "deny"? Does the tool result come back as an error message? An empty string? Or something else?

The denial reason is returned to the model as the tool result. The model sees it the same way it would see any tool output — it reads the text and decides what to do next. This is how a hook communicates intent without modifying the system prompt mid-run.

Section 05

The PostToolUse Audit

Analogy — the surgeon's sponge count

After every surgical procedure, the scrub nurse counts every sponge, instrument, and suture used during the operation. This happens automatically as part of the closing protocol — it doesn't wait for the surgeon to remember to ask. The count goes into the surgical record: what was used, in what quantity, in what order.

You don't do this to catch problems. You do it so that if something goes wrong later, you have an exact, timestamped, machine-readable record of what happened.

Why it matters — structured audit trail

Right now, when Morning Spark runs, you can read the terminal output. But terminal output is for humans — it doesn't survive a crash cleanly, can't be queried later, and has no structure. A JSONL span trace is the code-readable equivalent: one line per tool call, structured, append-only, always accurate.

This is the foundation for every observability tool you'll use in production AI systems: cost tracking, latency measurement, debugging, compliance logging.

In the SDK
async def post_tool_use_audit(input_data, tool_use_id, context):
    result_text = str(input_data.tool_response)
    span = {
        "timestamp": datetime.utcnow().isoformat() + "Z",
        "tool_name": input_data.tool_name,
        "tool_input": input_data.tool_input,
        "result_length": len(result_text),
        "result_preview": result_text[:120],
        "tool_use_id": tool_use_id,
    }
    _hook_state["spans"].append(span)

    span_path = Path(__file__).parent / "morning-spark_spans.jsonl"
    with open(span_path, "a", encoding="utf-8") as f:
        f.write(json.dumps(span) + "\n")

    return {}

After the run, open morning-spark_spans.jsonl. Each line is a JSON object. You can see the exact order tools were called, the parameters used, the result length, and when each call happened. The file grows with every run — it's cumulative.

Section 06

The Act-Strategy Gap — Closed

Two cycles of evidence led to this hook design. It's worth tracing the line explicitly.

CycleWhat the agent didThe gapRung 6 fix
Cycle 4
mac-advisor		 Detected a thermal contradiction, computed the right next action, printed it to the terminal The model never saw the computed remediation — it was printed outside the model's context PreToolUse injects the pending item into the hook's denial reason, which the model receives as a tool result
Cycle 5
research-lead		 Detected insufficient-data reports, re-dispatched follow-up agents to the same sources Same source + same params = same result. "Try again" ≠ "try differently" PreToolUse tracks every (tool_name, params) pair. Denies repeats with an explicit variation instruction

The pattern: both gaps had the same root cause — remediation logic running in Python-land, invisible to the model. The model can only adapt based on what arrives in its context. Hooks create a channel from your Python code directly into the model's next decision.

Section 07

The Five Tools

Morning Spark registers five tools in an MCP server named spark. The SDK prefixes them with mcp__spark__ in the model's tool list.

ToolArgsReturnsSide effect
fetch_weather none Weather forecast string Sets _agent_state["weather"]
fetch_date none Date and day string Sets _agent_state["date_info"]
fetch_headline category: str Top headline for category Sets _agent_state["headline"] + category
check_quality none {"quality_passes": bool, "issues": [...]} Sets _agent_state["quality_passed"]
synthesize_briefing none {"status": "complete", "briefing": "..."} Sets _agent_state["briefing"]; writes briefing_log.json

Valid headline categories: general, technology, science, health, world, business

None of these tools make real HTTP calls — they return simulated data. This is by design: the learning objective is hooks, not API integration. In a real agent you'd replace each _impl function with a live fetch; the hooks would be identical.

Natural hook surface

The key design choice behind Morning Spark: fetch_headline takes a category parameter. That means the PreToolUse guard has something concrete to dedup — it can tell the difference between fetch_headline(category="technology") and fetch_headline(category="science"). The hook can let the second call through even after blocking the first.

Section 08

Goal Predicate — How the Agent Knows It's Done

Every agent needs a precise, code-checkable definition of success. Morning Spark's is:

def briefing_complete() -> bool:
    return (
        _agent_state.get("weather") is not None
        and _agent_state.get("date_info") is not None
        and _agent_state.get("headline") is not None
        and _agent_state.get("quality_passed", False)
        and _agent_state.get("briefing") is not None
    )

All five conditions must be true simultaneously. The agent loop checks this after every model turn. The loop exits only when this function returns True.

What happens if it never returns True? Two hard caps enforce a principled exit: MAX_LOOP_TURNS = 6 and MAX_TOOL_CALLS = 12. If either cap fires, the loop exits with an "incomplete" summary rather than running forever.

Why the quality check is in the predicate

The agent could synthesise a briefing without checking quality first — it has weather, date, and headline. But the predicate requires quality_passed=True. This forces the model to call check_quality explicitly, making the quality gate visible in the tool trace and in the spans file. If you remove quality_passed from the predicate, the agent skips it and goes straight to synthesis. The predicate shape is the policy.

Section 09

App Memory — The Cross-Day Guard

Morning Spark writes a small memory file after every successful run: briefing_log.json.

{
  "last_run": "2026-06-14T07:23:11Z",
  "date": "Saturday, June 14, 2026",
  "headline_category": "technology",
  "headline_preview": "AI chip shortage eases as TSMC ramps 2nm production...",
  "briefing_preview": "Good morning! Here's your brief for Saturday, June 14..."
}

The next time the agent runs, it reads this file at boot. Yesterday's headline_preview gets injected into the system prompt:

"Yesterday's top topic: AI chip shortage eases as TSMC ramps 2nm production. If today's headline is similar to yesterday's topic, try a different category."

This is the cross-day guard: the model is nudged to choose a different headline category if today's top story is about the same thing as yesterday's. On first run, the file doesn't exist and the guard text is omitted.

Why this qualifies as "memory"

It's not just logging. The file's content changes what the model decides on the next run. That causal link from a past run to a future decision is what distinguishes app memory from a log file.

Section 10

Module-Level State — The Shared Blackboard

Morning Spark uses two module-level dictionaries that live at the top of main.py, outside any function.

# Reset before each run
_agent_state: dict = {
    "weather": None,
    "date_info": None,
    "headline": None,
    "headline_category": None,
    "quality_passed": False,
    "quality_issues": [],
    "briefing": None,
}

_hook_state: dict = {
    "calls_made": [],   # (tool_name, params_json) tuples seen by PreToolUse
    "spans": [],          # PostToolUse span records
    "denied_count": 0,  # how many PreToolUse denials fired this run
}

Why module level?

Hooks run inside the SDK's execution path. They cannot return values to your loop directly — they return their output to the SDK. The only way to pass state from a hook to your loop (or from a tool to a hook) is via a shared location that both can reach: a module-level variable.

Think of it as a blackboard in a shared office. The hook writes to it. The loop reads from it. Neither needs to call the other directly. This is the canonical inter-component state-sharing pattern in the SDK.

Both dicts are reset to their initial values at the start of every run. This ensures clean state even if you run the agent multiple times in the same Python session.

Section 11

The Agent Loop — What Will Happen at Runtime

Here's the full sequence Morning Spark executes every time you run main.py:

  1. Boot — print [AGENT BOOT], reset state dicts, check for briefing_log.json
  2. Build system prompt — inject yesterday's topic guard if log exists
  3. Register hooks — ClaudeAgentOptions(hooks={...}) wraps both functions
  4. Print goal — [GOAL SET] briefing_complete = False
  5. Enter SDK client — async with ClaudeSDKClient(options=options) as client
  6. Turn 1 — send initial prompt → model selects first tool(s)
  7. Each tool call:
    • [PRE-TOOL GUARD] fires → prints allow or deny decision
    • If allowed: tool impl runs → [TOOL CALL] printed → state updated
    • [POST-TOOL AUDIT] fires → writes JSONL span
    • If denied: model receives denial text → adapts next call
  8. After each turn: [LOOP FEEDBACK] — check goal predicate
  9. Goal met: [GOAL PREDICATE] True → print briefing → print span summary → exit
  10. Cap hit: print incomplete notice → print spans so far → exit

Typical happy path: Turn 1 → fetch_weather, fetch_date, fetch_headline (3 tool calls, 3 spans written). Turn 2 → check_quality, synthesize_briefing (2 more). Goal met after turn 2. Total: 5 tool calls, 5 spans, loop exits cleanly.

Section 12

What to Watch For During Your Run

When you run main.py, look for these specific moments:

1. The PreToolUse guard firing for the first time

The first time each tool is called, the guard prints [PRE-TOOL GUARD] ALLOW. This is normal. Watch for the first time it prints [PRE-TOOL GUARD] DENY — this means the model tried to repeat a call the hook had already seen.

2. A denial followed by a different category

If the model tries fetch_headline(category="technology") twice and the second attempt is denied, watch what it does in the next turn. Does it pick a different category? Does it skip headline and go straight to check_quality? This is the act-strategy adaptation in action.

3. The spans file being created

After the run exits, open morning-spark_spans.jsonl. Count the lines. Each line should match a successful tool call (denials don't get a span — the tool never ran). Cross-reference with the terminal output to verify they match.

4. The goal predicate check

Watch for [GOAL PREDICATE] in the terminal. It fires after each turn. On the first turn it should be False (quality and briefing not yet done). By the second or third turn, if everything went cleanly, it should flip to True and the loop should exit.

5. The log file after exit

Open briefing_log.json. This is the app memory file that the cross-day guard will read on your next run. Check that it contains a real headline_preview and briefing_preview from this run.
