§2

Three Bugs, One Success

Each bug lived at a different layer of the execution pipeline. The first was in your Python code. The second was in how the SDK delivers data to your hooks. The third was in the SDK's own permission system — hidden behind output that looked like success.

B1
Windows %-d format string — found at smoke test collection
datetime.now().strftime('%A, %B %-d, %Y') worked on Linux (zero-pad suppression) but raised ValueError: Invalid format string on Windows. Fix: replace %-d with _now.day (integer). Discovered before the first real run.
B2
Hook input_data is a dict, not an object — Run 1
The SDK passes input_data to PreToolUse and PostToolUse as a plain Python dict. getattr(dict_obj, "tool_name", "?") always returns "?" — Python dicts have no attributes with that name. Every tool call hashed to ("?", "{}"); ToolSearch registered it first; every subsequent MCP tool was denied as a duplicate. Fix: _get_field(obj, field, default) helper that branches on isinstance(obj, dict).
B3
dontAsk without allowed_tools silently denies all MCP tools — Run 2
After the dict fix, PreToolUse correctly said ALLOW for every MCP tool. But PostToolUse never fired for any of them, and the model said "The weather tool was denied." The SDK's permission layer — a separate check that runs after PreToolUse — denied all MCP tools because permission_mode="dontAsk" was set without an allowed_tools list. No list means no whitelist; no whitelist means no MCP tools allowed. Fix: add ALL_ALLOWED with all 5 tool names.
✓
Run 3 — goal met in one turn
With all three fixes applied and 32/32 smoke tests green, the agent ran clean. All 5 MCP tools executed, 6 spans written, briefing produced, briefing_log.json written. Cost $0.71, 1/6 turns used.
§3

PreToolUse — The First Gate

PreToolUse fires before the tool executes. It receives the tool name and input, and it can either allow the call to proceed or deny it with a reason the model reads. It is the earliest interception point in the SDK's execution pipeline.

🔧 [TOOL CALL] fetch_weather({}) ✅ [PRE-TOOL GUARD] ALLOW · mcp__spark__fetch_weather({}) ← our hook ran, said ALLOW 📋 [POST-TOOL AUDIT] span written · mcp__spark__fetch_weather · 151 chars ← tool ran ┆ UserMessage: ToolResult(id=toolu_01…) ← result delivered to model

PreToolUse is where the dedup guard lives. Every time a tool call arrives, the guard checks whether it has already seen this exact (tool_name, params_json) pair. If yes — deny with a variation instruction. If no — record the signature and allow.

What PreToolUse can't do
Returning ALLOW from PreToolUse does not guarantee the tool will run. Two things can still stop it: the SDK's own permission layer (Bug 3), or the MCP server failing to respond. PreToolUse is the first gate, not the only one.

In run 3, the guard fired ALLOW six times and denied zero times. The model called each tool exactly once in the right sequence — no repeats, so the guard had nothing to intercept. The guard's value is proportional to how badly the model gets stuck. A clean run makes it invisible.

§4

PostToolUse — The Silence Was Diagnostic

PostToolUse fires after the tool's return value exists — not after PreToolUse says ALLOW, but after the tool actually ran and returned data. It is execution proof. If PostToolUse fires, the tool ran. If it doesn't, something stopped the tool between ALLOW and execution.

In run 2, this was the entire diagnostic. PreToolUse printed ALLOW for every MCP tool. But no PostToolUse line followed — not for fetch_weather, not for fetch_date, not for any MCP tool. The silence between ALLOW and the next print was not a logging gap; it was evidence that the execution never happened.

── Run 2 (bug still present) ────────────────────────────────── ✅ [PRE-TOOL GUARD] ALLOW · mcp__spark__fetch_weather({}) ┆ UserMessage: ToolResult(id=toolu_01…) ← ToolResult exists, but contains SDK denial ← no 📋 [POST-TOOL AUDIT] — tool never ran ── Run 3 (fixed) ────────────────────────────────────────────── ✅ [PRE-TOOL GUARD] ALLOW · mcp__spark__fetch_weather({}) 📋 [POST-TOOL AUDIT] span written · mcp__spark__fetch_weather · 151 chars ┆ UserMessage: ToolResult(id=toolu_01…) ← ToolResult carries the actual weather string
Auditor analogy
An auditor doesn't mark a payment complete when the CFO approves the wire. They mark it complete when the bank confirmation lands. PostToolUse is the bank confirmation — it only exists when the transaction completed. ALLOW is the CFO's signature. These are different events on different systems.

In run 3, six PostToolUse spans were written — one for each tool call that actually ran. result_length in each span tells you how many characters came back. A span with result_length: 0 would mean the tool ran but returned nothing — execution happened, but the fetch produced no content. That's a different failure mode from "tool never ran."

§5

The Two-Gate Permission Pipeline

This is the core lesson of Cycle 6. There are two independent permission checks between a tool call arriving and the tool executing. Both must pass. Neither tells you whether the other passed.

Step 1
PreToolUse hook
our code · ALLOW/DENY
→
Step 2 ← Bug 3 lived here
SDK permission layer
allowed_tools check
→
Step 3
Tool executes
MCP server runs impl
→
Step 4
PostToolUse hook
our code · span written

In run 2, step 1 (PreToolUse) passed. Step 2 (SDK permission) failed silently — because permission_mode="dontAsk" was set without an allowed_tools list. The SDK had no whitelist of approved tools, so it denied all MCP tools by default. Steps 3 and 4 never ran. The model received a denial inside the ToolResult and said "The weather tool was denied" — even though our hook had just said ALLOW.

The deceptive output
In run 2, the terminal showed: ALLOW (green checkmark) → ToolResult → model says "denied." From the outside this looks like the ALLOW was ignored. What actually happened: ALLOW passed gate 1; gate 2 denied without printing anything; the denial message went into the ToolResult the model read. Gate 1 and gate 2 have completely independent outputs.
The fix
Add allowed_tools=ALL_ALLOWED to ClaudeAgentOptions. This gives the SDK's permission layer a whitelist. With dontAsk and a whitelist: any tool on the list is allowed silently; any tool not on the list is denied silently. Harness tools like ToolSearch are auto-allowed and bypass this check entirely — which is why ToolSearch worked in all three runs while our MCP tools failed in run 2.
## Pattern: always set allowed_tools when using dontAsk ALL_ALLOWED: list[str] = [ "mcp__spark__fetch_weather", "mcp__spark__fetch_date", "mcp__spark__fetch_headline", "mcp__spark__check_quality", "mcp__spark__synthesize_briefing", ] ClaudeAgentOptions( ... allowed_tools=ALL_ALLOWED, permission_mode="dontAsk", ... )
§6

Module-Level State — The War Room Whiteboard

Hooks fire inside the SDK's execution pipeline — not inside your agent loop. They run in a different call stack from the while loop_state["turns"] < MAX_LOOP_TURNS: block. For the hooks and the loop to share information, the state they both read and write must live at the module level — visible to any function in the file.

Consulting analogy
A consulting team uses a war room whiteboard. Each consultant updates their section when they finish a task. The project lead reads it after each round to check overall progress. If each consultant had a personal notepad that stayed in their pocket, the project lead would never know what they found — the state would exist but not be shared.

_agent_state is the whiteboard. _fetch_weather_impl, pre_tool_use_guard, post_tool_use_audit, and briefing_complete() all read the same object. When the weather tool runs and writes _agent_state["weather"] = _MOCK_WEATHER, the next thing to read that key — wherever it runs — sees the update immediately.
## Module level — the shared whiteboard _agent_state: dict = {"weather": None, "date_info": None, ...} _hook_state: dict = {"calls_made": [], "spans": [], ...} ## Tool impl writes to the whiteboard async def _fetch_weather_impl(args: dict) -> dict: _agent_state["weather"] = _MOCK_WEATHER ← whiteboard updated return {"content": [{"type": "text", ...}]} ## PreToolUse reads the call log to detect repeats async def pre_tool_use_guard(input_data, tool_use_id, context) -> dict: if sig in _hook_state["calls_made"]: ... ← same whiteboard ## Goal predicate reads final state def briefing_complete() -> bool: return _agent_state["weather"] is not None and ... ← same whiteboard

In run 3, after fetch_weather ran, _agent_state["weather"] was set to the mock weather string. The next time briefing_complete() ran — at the end of turn 1 — it found that key non-None and counted it as True. The whiteboard connected the tool execution to the goal check without any explicit passing of data between functions.

§8

Goal Predicate Walk-Through

After turn 1, the loop printed:

📊 [GOAL PREDICATE] weather=True · date=True · headline=True · quality=True · briefing=True 🔄 [LOOP FEEDBACK] turn 1 done · tool_calls=6 · briefing_complete=True ✅ [GOAL MET] briefing_complete() returned True. Exiting loop.

All five parts of the compound predicate flipped to True in the same turn. Let's trace how each one flipped:

  • weather=True — _fetch_weather_impl set _agent_state["weather"] = _MOCK_WEATHER
  • date=True — _fetch_date_impl set _agent_state["date_info"] = _MOCK_DATE
  • headline=True — _fetch_headline_impl set _agent_state["headline"] = _MOCK_HEADLINES["technology"]
  • quality=True — _check_quality_impl found all three non-None; set _agent_state["quality_passed"] = True
  • briefing=True — _synthesize_briefing_impl found quality_passed=True; assembled the briefing; set _agent_state["briefing"] = ...

The predicate is a chain: each stage depends on the one before it. check_quality can only pass if weather, date, and headline are all non-None. synthesize_briefing can only succeed if quality_passed is True. The tool sequence the model chose exactly matched the dependency order — not because the code forced it, but because the system prompt described the dependency and the model reasoned about it.

§9

The Model's Own Choices

The model made three autonomous decisions during the run that the code didn't prescribe:

1. Call ToolSearch first

Before calling any of your 5 MCP tools, the model issued a ToolSearch call to load their schemas. The system prompt didn't say to do this. The SDK presents ToolSearch to the model as a way to discover available tools, and the model chose to use it. This is why ToolSearch appeared in the span file every run — it's the model's own initialization step.

2. Call fetch_date and fetch_headline in parallel

The model's second response body contained both fetch_date and fetch_headline as separate ToolUseBlocks. The SDK executed them both, fired their hooks, and returned two ToolResult blocks. The model decided these two fetches were independent and could be issued in the same turn — correct. Weather was fetched first (separate response), then date + headline together, then quality check, then synthesis.

3. Choose "technology" as the headline category

The system prompt listed six valid categories. The model chose technology. There was no cross-day guard on the first run (no briefing_log.json existed yet), so no steering constraint was applied. That choice was entirely the model's. On a second run, the cross-day guard would read yesterday's headline_preview and inject a note into the system prompt if the category looked similar — that's the app memory's role in G2.

§10

The Guard That Never Fired

Zero PreToolUse denials in run 3. The dedup guard — the main rung 6 teaching point — was completely idle. The model called every tool exactly once and never repeated a signature.

Insurance pattern
A fire extinguisher in a building doesn't fail if it goes unused during a year. Its value is proportional to what happens if it's needed and not there. The dedup guard works the same way: in a clean run, it's invisible. In a stuck run — where the model tries the same tool with the same parameters three times because it can't make progress — it fires, delivers a variation instruction, and the model adapts. Zero denials is the best outcome, not a sign the guard is useless.

The G3 teaching point (observe–reason–act) is demonstrated most clearly when the guard fires. In runs 1 and 2, when all tools resolved to ("?", "{}") due to the dict bug, the guard fired 11 times. The model observed the denial reasons and reasoned about them — but could not adapt because the denial reason said "duplicate detected" for tools that had never actually run. The O-R-A loop was working; the environment was broken.

The act-strategy adaptation gap from Cycle 5 also surfaced here in the post-run probes. When a real weather API returns a 503 error, calling fetch_weather again with the same parameters won't help — the guard's dedup logic correctly blocks it. What you actually need is a different tool: a backup weather source. The guard can deny the repeat; the fallback requires a second tool registered on the server. That's act-strategy adaptation: change the resource, not the retry count.

§11

What Rung 6 Teaches

Hooks are not wrappers around the agent loop — they are interceptors inside the SDK's execution pipeline. The pipeline looks like this:

The mental model to keep
Tool call arrives → PreToolUse fires (can deny) → SDK permission check (can deny) → Tool executes → PostToolUse fires (always, if execution happened) → Result to model.

Silence at any step after ALLOW means something stopped execution between that step and the next. PostToolUse silence after PreToolUse ALLOW = the SDK permission layer denied it. The way to observe which step failed: look at what didn't print, not just what did.

Three gotchas now in the registry from this cycle:

  • hook-input-is-a-dict — use dict.get() or a _get_field() helper; getattr() on a dict always returns the default
  • dontAsk-requires-allowed-tools — always set allowed_tools when using permission_mode="dontAsk", or all your MCP tools are silently denied
  • (carried from Cycle 5) act-strategy adaptation — when a tool fails, change the tool, not the retry count

Rung 6 closes the act-strategy gap from Cycle 5 in morning-spark's domain. The PreToolUse guard detects when the model is stuck (same params, same tool) and injects a variation instruction before the call executes. That's the hook as a strategy enforcer, not just an audit tool.
