§1 · Use case

What this agent is for

Recipe Companion helps you cook one meal end-to-end. You name a recipe — say, spaghetti carbonara — and the agent looks it up, checks each ingredient against the pantry you already have, builds a shopping list for what you're missing, and sets the first cooking timer when you're ready to start. After the first session it remembers your pantry, your favorites, and what's on your shopping list, so the second time you cook the same meal it picks up where you left off.

What makes this agent different from the previous two: it can call a chain of tools without ever returning to your Python code between them. The model decides to check the pantry for eggs, sees the result, decides to check for flour, sees that, decides to add yeast to the shopping list — all inside what looks like a single "model response" from your code's perspective. You'll see this in the run output as a new label: [TOOL CHAIN] N tool calls in this turn.

§3 · The agentic core

What makes this an "agent"

The three core traits are present, but two of them get sharper this cycle.

Goal-directedness — it knows when the meal is set up

The agent has a real "am I done?" check it runs every turn. Done means: the recipe got looked up, every ingredient got checked against the pantry, the shopping list got updated for whatever was missing, and the first cooking timer was set. When all four of those are true, the agent says it's ready to cook and exits. (You can also tell it to stop at any time by typing stop; or it will stop itself at a safety cap of eight turns.)

Autonomy — the model picks the chain, not just the next move

In Cycle 2 the model picked one action per turn — "ask," "assess + ask," or "done." Cycle 3 deepens that: the model picks sequences of actions, inside a single response. When you say "I want to cook spaghetti carbonara," the model decides on its own to look up the recipe first, then check each ingredient in turn, then add missing items to the shopping list — and it does all of those things before your Python sees the message come back. The autonomy isn't just "what tool do I pick?" It's "what chain of tools makes sense for this situation?"

Observe → reason → act, now at three speeds

The loop closes at three different scales this cycle:

  • Within a single tool chain (fastest, new this cycle) — the result of check_pantry("eggs") shapes whether the next call is check_pantry("flour") or add_to_shopping_list("eggs"). Both happen inside the same model turn; your Python doesn't see the back-and-forth.
  • Within a session (carried from Cycle 2) — turn 3's question is shaped by turn 2's user reply.
  • Across sessions (carried from Cycle 2) — tomorrow's first turn reads yesterday's pantry and favorites.

§5 · Reading the code (a tiny Python primer)

You do not need to write Python to read this agent. You need to recognize five constructs (same as last cycle):

  • def name(args): … and async def name(args): … — named recipes; async is the async-flavored one used for tools.
  • while CONDITION: … — keep doing the indented block until the condition turns false.
  • if … : … else: … — a branch.
  • print("…") — show this text in the terminal.
  • await something() — wait here until something() comes back. Black box.

One new thing to recognize in this cycle's code: the @tool("name", "description", {...}) line that appears just before each async function near the top of main.py. That's a decorator — it's the line that registers a Python function with the SDK as a tool the model can call.

Recommended reading order:

  1. Top of main.py — module docstring + constants. Skim the comments labelled PURPOSE.
  2. Find the five @tool-decorated functions. Each is short — about 10 lines — and the schema is right there in the decorator. These are your registered tools.
  3. session_complete() — the goal predicate; 10 lines.
  4. agent_loop() — the main story. Find the async with open_sdk_client(...) as client: line — everything inside that block is one continuous conversation with the model, with tools wired in.
  5. _tool_observer() — short, but worth reading: this is where the [TOOL CHAIN] N tool calls in this turn line gets its number.
  6. Finish with print_summary() — pure formatting.

§7 · Watch for these moments

Things worth noticing during the run

The headline moment

Look for 🔗 [TOOL CHAIN] N tool calls in this turn — that single line is the rung-4 capability landing in plain English. In Cycle 1 and Cycle 2, the number on a comparable line would always have been 1 (or 0). Now it can be 5, 8, 12. Your Python never saw those calls happen — the SDK ran them, fed each result back to the model in the same turn, and only handed control back to your code when the model was done thinking.

Three memory layers, three different labels

💾 [SESSION MEMORY] is the model's own memory of the conversation (carried from Cycle 2). 📀 [APP MEMORY] is the JSON ledgers on disk (carried from Cycle 2). 🔗 [TOOL CHAIN] is the new third dimension — the model orchestrating tools without round-tripping to your code. They do different jobs.

Token cost shape is different from Cycle 2

In Cycle 2's study-buddy run, turn 1 was huge (~13K input tokens) and turns 2–5 each used about 2 input tokens. This cycle's first turn is also big, but it ALSO does more work — eight tool calls happen inside it. The cost-per-useful-action can actually go DOWN at rung 4 because you stop paying for re-prompting overhead between every tool call. Worth watching the dollar figure at exit and dividing it by total tool calls.

Run it twice on the same recipe

On the second run, the pantry will be the same and the shopping list will already have what you needed last time. The agent's first turn will look different — it'll notice it has everything (or remember what's pending) and act accordingly. Same code; behavior changes because of what was saved last time.

The log accumulates

recipe-companion_run_output.log is appended every run, never overwritten. Useful for cross-run comparison (which you'll do explicitly in later cycles).

§8 · Gotchas

Watch out for these

  1. You type a recipe the demo doesn't know. The demo DB has a small set (spaghetti carbonara, pancakes, omelette, chicken stir fry, simple salad). If you type something else, lookup_recipe returns a "not found" error and the model is expected to apologize and offer one of the known ones. Watch how it handles the error — that's a real-tool-error moment that wouldn't have looked the same in Cycle 2.
  2. Empty pantry on a fresh disk. The agent ships with pantry.json seeded with about ten common items so the first run isn't pathological. If you delete or empty that file, the agent will report nearly everything as missing — that's not a bug; that's what the agent should do when your pantry is empty.
  3. The model takes more than one turn to finish. A complex recipe might have the model do one big chain in turn 1, then ask you a clarifying question, then chain a few more tools in turn 2 (e.g., "are you OK with the substitutes?"). That's normal — the loop allows up to eight turns and twenty total tool calls.
  4. A timer "set" is actually a print. set_timer doesn't really schedule anything in the OS — it announces and logs the timer. Don't expect a real notification at the 8-minute mark. This is intentional for the demo; production would wire it to a real scheduler.
  5. The plan changes mid-run. If the model sees a tool result that surprises it ("oh, pantry has rare ingredient X"), it may revise the chain and call a different mix of tools than it would have. You'll see a 📝 [PLAN REVISED] line. That's autonomy, not a bug.

If you replaced the model with a hardcoded sequence ("look up, check 6 ingredients in order, add missing ones, set timer for 8 minutes"), you'd have a recipe-prep program — not an agent. The agency lives in every row where the model owns the call.

§10 · SDK glossary

  • @tool(name, description, schema) — Python decorator from the SDK; turns an async function into a registered tool the model can call. The schema is a dict of `{param_name: type}`.
  • create_sdk_mcp_server(name, version, tools=[...]) — bundles tools into a logical "server" the SDK can wire into the client.
  • ClaudeAgentOptions(mcp_servers={key: server}, allowed_tools=["mcp__<key>__<tool_name>", ...]) — wires the server into the agent options. The model can only call tools listed in allowed_tools.
  • ToolUseBlock — the message-block type the SDK emits when the model asks to call a tool. Your code can observe these as they fire.
  • ToolResultBlock — the message-block type the SDK emits when a tool returns a result (handed back into the same response, fed to the model).
  • Rung 4 — the SDK ladder rung introduced by this agent: custom tools via @tool + create_sdk_mcp_server; model-orchestrated tool chains.

§11 · Self-check

A few self-check questions

Three quick questions. Click Reveal for each after you've picked an answer.

1. When the model "chains" 8 tool calls inside one response, how many times does control return to your Python code during those 8 calls?
Zero times. That's the whole point of rung 4. The SDK runs each tool, feeds the result straight back into the model's response in progress, and only returns control to your Python when the model is done. In Cycle 2's JSON-dispatch pattern, you would have had 8 round trips through your Python loop; here you have one.
2. If you removed all five @tool decorators but kept the tool function bodies intact, what would happen at run time?
The model would have no tools to call. The decorator is what registers each function with the SDK as a callable tool. Without it, the functions are just plain Python that the model has no way to invoke. The agent would still run, but it would talk in prose rather than taking action.
3. You run the agent twice — once on a Monday, once on a Friday — both times for "pancakes." On Friday the agent skips checking flour and eggs and just asks if you want to add maple syrup to the shopping list. Why?
The agent read the pantry ledger on Friday. This is across-session memory in action (rung 3, carried). The pantry survived between runs as a JSON file; the agent reads it before turn 1 and can avoid redundant work the second time. Python doesn't "cache" in the traditional sense — it just reads what's on disk.
